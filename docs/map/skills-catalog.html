System map · a part

skills-catalog

What's inside skills-catalog, and which piece uses which?

One program on each machine: the MCP server Claude Code talks to, and the CLI for a person at a terminal. It sets itself up (skills-catalog setup, undone by teardown), publishes, searches, installs, and keeps installed skills up to date; its rules reviewer flags what a new version adds, and an update that could run something new waits for the person's yes.

Decisions
B3 Risky updates wait for a yes built

auto-updates are on by default; an update waits for the Developer's yes only when it could change what runs on the machine or the reviewer flagged it, on every surface. While the Assistant runs commands without asking, a newly added command in a skill's text is flagged too.

Chosen over applying every update silentlyholding every update

Why A skill is instructions the Assistant follows, so an update can change what runs; asking about every update trains people to say yes

The owner · 2026-09-28, narrowed 2026-09-29

Why The Developer's own setting for that skill decides, not the Assistant

B23 What a version is built

About installer (skills-catalog)

Use-case steps through skills-catalog

  1. 1publish, step 2: Claude Code calls publish_skill_to_catalog, which shows a preview first: the files it would send, any it skips, and what the rules reviewer flags
  2. 1publish, step 4: Or Developer 1 publishes from a terminal: skills-catalog publish, which previews and asks
  3. 1publish, step 5: v1 goes into the catalog, with its fingerprint and its review; a skill missing a name, description or body is refused, and nothing is stored
  4. 2discover, step 2: Claude Code calls search_shared_skills
  5. 2discover, step 3: The catalog finds release-note-draft; when nothing fits, it says so, and shows the closest only as close
  6. 3retrieve, step 2: Claude Code calls read_shared_skill, then install_shared_skill
  7. 3retrieve, step 3: Every file of v1 is fetched, and checked against its fingerprint
  8. 3retrieve, step 4: The skill lands in .claude/skills, byte for byte as published, ready to use
  9. 4version, step 2: Claude Code calls publish_skill_to_catalog: the preview names the new script
  10. 4version, step 3: The rules reviewer flags the new script (skills-catalog review reruns the reviews of a local catalog)
  11. 4version, step 4: v2 is stored; v1 stays, and the history shows both
  12. 4version, step 5: Developer 2's list shows ↑ v2 available
  13. 5held update, step 2: Claude Code calls update_installed_skills
  14. 5held update, step 3: v2 is fetched
  15. 5held update, step 4: v2 adds a script that can run on this machine: held
  16. 5held update, step 5: Claude Code shows the held update and asks one question
  17. 5held update, step 6: In a terminal, Developer 2 looks at the change (skills-catalog diff) and takes it (update --accept); or says yes to Claude Code
  18. 6setup, step 1: skills-catalog setup: a welcome, then one question, auto-updates on? (yes by default); --yes or --config for no questions
  19. 6setup, step 2: Claude Code gets the MCP server (skills-catalog mcp) and a session-start hook
  20. 6setup, step 3: In AWS: skills-catalog login signs in with GitHub once (on one machine there is nothing to sign in to)
  21. 6setup, step 4: skills-catalog teardown undoes everything setup wrote
