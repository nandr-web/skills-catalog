1 · publish · on one machine

1publish

Developer 1 says

“Publish my skill in ./release-note-draft”
  1. 1Developer 1 asks Claude Code to publish the folder
  2. 2Claude Code calls publish_skill_to_catalog, which shows a preview first: the files it would send, any it skips, and what the rules reviewer flags
  3. 3Developer 1 says yes
  4. 4Or Developer 1 publishes from a terminal: skills-catalog publish, which previews and asks
  5. 5v1 goes into the catalog, with its fingerprint and its review; a skill missing a name, description or body is refused, and nothing is stored
Real screens
publish.png
Checked by
  • publish A developer publishes a skill (manifest + supporting files); it is available to others, complete.
  • publish-rejects-invalid A skill missing a name, description or body is rejected with an explanation; nothing partial is stored.

2 · discover · on one machine

2discover

Developer 2 says

“Is there a skill for writing release notes?”
  1. 1Developer 2 asks in plain words
  2. 2Claude Code calls search_shared_skills
  3. 3The catalog finds release-note-draft; when nothing fits, it says so, and shows the closest only as close
  4. 4A table: name, version, who published it, what it does
Real screens
search.pngclosest.png
Checked by
  • discover Through an AI assistant, in natural language, a developer finds skills matching a need; each result has a name and description.
  • discover-nothing-matches When nothing matches, the assistant clearly says so.

3 · retrieve · on one machine

3retrieve

Developer 2 says

“Install it in this project”
  1. 1Developer 2 asks to install it
  2. 2Claude Code calls read_shared_skill, then install_shared_skill
  3. 3Every file of v1 is fetched, and checked against its fingerprint
  4. 4The skill lands in .claude/skills, byte for byte as published, ready to use
Real screens
reel-install.gif
Checked by
  • retrieve Through an AI assistant, a developer retrieves a named skill, complete and unchanged.
  • consistency A retrieved skill is complete and unchanged from what was published.

4 · version · on one machine

4version

Developer 1 says

“Publish the new version”
  1. 1Developer 1 publishes again: v2 adds a script
  2. 2Claude Code calls publish_skill_to_catalog: the preview names the new script
  3. 3The rules reviewer flags the new script (skills-catalog review reruns the reviews of a local catalog)
  4. 4v2 is stored; v1 stays, and the history shows both
  5. 5Developer 2's list shows ↑ v2 available
Real screens
list.png
Checked by
  • version-new Publishing an existing name creates a new version; prior versions are retained; nothing is silently overwritten.
  • version-history-visible A developer can see a skill's version history, and the change is visible.
  • review-flags A built-in rules reviewer flags scripts, tool grants, a publisher change, prompt-injection patterns and context cost; findings are grounded; a clean skill gets none.

5 · held update · on one machine

5held update

Developer 2 says

“Update my shared skills”
  1. 1Developer 2 asks for updates (or a new session's hook says one waits)
  2. 2Claude Code calls update_installed_skills
  3. 3v2 is fetched
  4. 4v2 adds a script that can run on this machine: held waits
  5. 5Claude Code shows the held update and asks one question waits
  6. 6In a terminal, Developer 2 looks at the change (skills-catalog diff) and takes it (update --accept); or says yes to Claude Code
Waiting for a yes

v2 adds scripts/collect.sh, which can run on this machine. Developer 2 stays on v1 until they say yes.

Real screens
update.pngterminal.png
Checked by
  • auto-updates Auto-updates are on by default, global and overridable per skill; an update that raises a risk flag stops and shows it.
  • review-flags A built-in rules reviewer flags scripts, tool grants, a publisher change, prompt-injection patterns and context cost; findings are grounded; a clean skill gets none.

6 · setup · on one machine

6setup

Developer 2 says

“Set up skills-catalog”
  1. 1skills-catalog setup: a welcome, then one question, auto-updates on? (yes by default); --yes or --config for no questions
  2. 2Claude Code gets the MCP server (skills-catalog mcp) and a session-start hook
  3. 3In AWS: skills-catalog login signs in with GitHub once (on one machine there is nothing to sign in to)
  4. 4skills-catalog teardown undoes everything setup wrote
Checked by
  • setup-cli-and-agent Setup through a guided CLI, or by an assistant from the setup skill or the setup doc; welcoming and colourful; asks about auto-updates, default yes.
  • setup-unattended Unattended setup via CLI, passing all configuration or a file; the setting can be changed later by CLI or file.

skills-catalog

MCP server · CLI

One program on each machine: the MCP server Claude Code talks to, and the CLI for a person at a terminal. It sets itself up (skills-catalog setup, undone by teardown), publishes, searches, installs, and keeps installed skills up to date; its rules reviewer flags what a new version adds, and an update that could run something new waits for the person's yes.

Inside skills-catalog ›

catalog on AWS

API · DynamoDB · S3

The shared catalog in the team's AWS account: the API on Lambda behind CloudFront, versions in DynamoDB, files in S3, a search file kept up to date by an indexer. Each version is reviewed as it is published. Only the GitHub logins the deployment lists may sign in.
